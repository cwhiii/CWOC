# Requirements Document

## Introduction

This feature replaces the current name-based tag reference system with a unique-ID-based system. Currently, tags are identified by their name string everywhere — in settings, on chits, in rules engine conditions, in custom view filters, shared tags, kiosk selected tags, omni locked filters, and recent tags. This causes breakage when tags are renamed because all references become stale.

The new system assigns each tag a unique ID at creation time. All backend storage and internal references use the tag ID exclusively. Tag names become purely display-friendly labels that can be renamed freely without breaking any references. Users never see or interact with tag IDs directly — they only ever see tag names.

## Glossary

- **Tag_Registry**: The authoritative list of all tags for a user, stored in the settings JSON blob. Each entry contains a unique ID, display name, color, font color, and favorite flag.
- **Tag_ID**: A unique, immutable identifier assigned to each tag at creation time (UUID v4 format). Used internally for all references.
- **Tag_Name**: The user-facing display label for a tag. Mutable — can be renamed without affecting references.
- **Chit**: The core data record in CWOC that can serve as a task, note, calendar event, alarm, checklist, or project.
- **Rules_Engine**: The backend system that evaluates conditions and applies actions to chits based on configurable rules.
- **Custom_View_Filters**: Per-view saved filter/sort configurations stored in user settings, which can filter by tags.
- **Shared_Tags**: Configuration defining which tags are shared with other users and their access roles.
- **Kiosk_Selected_Tags**: Tags selected for display in kiosk mode.
- **Omni_Locked_Filters**: Default locked filter configuration for the Omni View, which can include tag filters.
- **Recent_Tags**: A list of recently used tags persisted in user settings for quick access.
- **System_Tags**: Auto-computed tags with the "CWOC_System/" prefix, generated by the backend based on chit properties. These are not user-created and do not need IDs.
- **Hierarchical_Tag**: A tag using "/" as a path separator to represent nested structure (e.g., "Work/Projects/CWOC").
- **Migration_Engine**: The inline startup migration system that applies schema changes to the SQLite database.

## Requirements

### Requirement 1: Tag Model with Unique ID

**User Story:** As a system administrator, I want each tag to have a unique immutable identifier, so that all internal references remain stable regardless of name changes.

#### Acceptance Criteria

1. WHEN a new tag is created, THE Tag_Registry SHALL assign a UUID v4 identifier to the tag that is unique across all tags for that user.
2. THE Tag_Registry SHALL store each tag as an object containing: id (string, UUID v4, 36 characters), name (string, 1 to 200 characters inclusive), color (string or null), fontColor (string or null), and favorite (boolean, default false).
3. WHEN a tag is renamed, THE Tag_Registry SHALL update only the name field while preserving the same Tag_ID, color, fontColor, and favorite values.
4. IF a tag creation request supplies a name that already exists for that user (case-insensitive comparison after trimming leading and trailing whitespace), THEN THE Tag_Registry SHALL reject the creation and return an error response indicating a duplicate name.
5. THE Tag_Registry SHALL preserve the Tag_ID for the lifetime of the tag — the ID is never reused, reassigned, or changed after initial assignment.
6. IF a tag creation request supplies a name that is empty or exceeds 200 characters, THEN THE Tag_Registry SHALL reject the creation and return an error response indicating an invalid name length.
7. WHEN a tag is renamed, IF the new name already exists for that user (case-insensitive comparison after trimming leading and trailing whitespace), THEN THE Tag_Registry SHALL reject the rename and return an error response indicating a duplicate name.

### Requirement 2: Chit Tag Storage by ID

**User Story:** As a backend developer, I want chits to store tag references as a list of Tag_IDs instead of name strings, so that renaming a tag does not break chit-tag associations.

#### Acceptance Criteria

1. THE Chit model SHALL store the tags field as a JSON-serialized list of Tag_ID strings, where each Tag_ID is a UUID v4 assigned by the Tag_Registry, with a maximum of 50 Tag_IDs per chit.
2. WHEN a chit is saved with tags, THE backend SHALL validate that each Tag_ID in the list corresponds to an existing tag in the Tag_Registry, reject the request with an error response indicating which Tag_IDs are invalid if any do not exist, and silently deduplicate any repeated Tag_IDs before persisting.
3. WHEN a chit is retrieved via the API, THE backend SHALL resolve each Tag_ID to its current name and return each tag as an object containing both the Tag_ID and the current display name.
4. IF a Tag_ID on a chit references a tag that no longer exists in the Tag_Registry, THEN THE backend SHALL omit that tag from the API response and log a warning to the server log including the orphaned Tag_ID and the chit ID.
5. WHEN a tag is renamed in the Tag_Registry, THE backend SHALL preserve the tag's existing Tag_ID so that all chits referencing that tag continue to resolve to the updated name without modification.

### Requirement 3: Rules Engine Tag Conditions by ID

**User Story:** As a user configuring automation rules, I want tag-based conditions to reference tags by ID, so that renaming a tag does not break my rules.

#### Acceptance Criteria

1. WHEN a rule condition uses the tag_present operator, THE Rules_Engine SHALL compare the condition value (a Tag_ID) against the Tag_IDs stored on the chit using case-sensitive exact match, returning true if the Tag_ID is found in the list.
2. WHEN a rule condition uses the tag_not_present operator, THE Rules_Engine SHALL verify the absence of the condition value (a Tag_ID) from the chit's Tag_ID list using case-sensitive exact match, returning true if the Tag_ID is not found.
3. IF a chit's tags list is null or empty, THEN THE Rules_Engine SHALL evaluate tag_present as false and tag_not_present as true.
4. WHEN a rule action adds a tag to a chit, THE Rules_Engine SHALL store the Tag_ID in the chit's tags list only if that Tag_ID is not already present in the list.
5. IF a rule action references a Tag_ID that does not exist in the Tag_Registry, THEN THE Rules_Engine SHALL skip that action and log a warning.
6. WHEN a rule condition or action stores a tag reference, THE Rules_Engine SHALL store the Tag_ID string, never the tag display name.

### Requirement 4: Custom View Filters by ID

**User Story:** As a user with saved view filters, I want my tag-based filters to reference tags by ID, so that renaming a tag does not break my saved views.

#### Acceptance Criteria

1. WHEN a custom view filter includes a tags filter, THE Custom_View_Filters SHALL store the filter values as a list of Tag_ID strings in the `tags` array of the view's filter configuration.
2. WHEN applying a custom view filter that contains Tag_IDs, THE frontend SHALL match chits whose tags list contains at least one of the specified Tag_IDs (OR logic), including hierarchical descendants whose resolved name starts with the filtered tag's resolved name followed by "/".
3. WHEN the frontend displays a custom view filter configuration, THE frontend SHALL resolve each Tag_ID to its current display name from the Tag_Registry.
4. IF a Tag_ID in a saved custom view filter no longer exists in the Tag_Registry, THEN THE frontend SHALL omit that entry from the displayed filter configuration and exclude it from filter matching.

### Requirement 5: Shared Tags by ID

**User Story:** As a user sharing tags with other users, I want the sharing configuration to reference tags by ID, so that renaming a shared tag does not break the sharing relationship.

#### Acceptance Criteria

1. THE Shared_Tags configuration SHALL store each entry with a `tag_id` field (the tag's unique identifier as assigned at tag creation) instead of a tag name field.
2. WHEN displaying shared tag configurations, THE frontend SHALL resolve the `tag_id` to the current tag name by looking up the tag in the owner's tags list from settings.
3. WHEN a shared tag is renamed by the owner, THE sharing configuration SHALL continue to grant the same access to shared users because the `tag_id` reference is unchanged and the sharing resolution logic matches chits by `tag_id`.
4. IF a `tag_id` in the Shared_Tags configuration no longer corresponds to any existing tag in the owner's tag list, THEN THE system SHALL exclude that entry from sharing resolution and THE frontend SHALL omit it from the displayed shared tag list.
5. WHEN the system encounters existing Shared_Tags entries that use a tag name string without a `tag_id`, THEN THE system SHALL migrate those entries by matching the tag name to the owner's current tag list and populating the `tag_id` field.

### Requirement 6: Kiosk Selected Tags by ID

**User Story:** As a user configuring kiosk mode, I want the selected tags to be stored by ID, so that renaming tags does not break kiosk configuration.

#### Acceptance Criteria

1. THE Kiosk_Selected_Tags setting SHALL store selected tags as a JSON array of Tag_ID strings (UUIDs), with a maximum of 50 entries.
2. WHEN displaying kiosk tag selections in the settings page tag picker, THE frontend SHALL resolve each stored Tag_ID to its current display name by looking up the Tag_ID in the settings tags array, and SHALL omit any Tag_ID that no longer matches an existing tag.
3. WHEN filtering chits for kiosk display via the /api/kiosk endpoint, THE backend SHALL match chits whose tags list contains the specified Tag_IDs by direct ID comparison.
4. WHEN a tag is renamed, THE system SHALL preserve the tag's existing Tag_ID so that all references in Kiosk_Selected_Tags remain valid without any update to the kiosk configuration.
5. IF a Tag_ID stored in Kiosk_Selected_Tags no longer corresponds to any tag in the settings tags array, THEN THE system SHALL silently skip that Tag_ID during kiosk filtering and display without returning an error.

### Requirement 7: Omni Locked Filters by ID

**User Story:** As a user with locked Omni View filters, I want tag-based locked filters to reference tags by ID, so that renaming tags does not break my Omni View configuration.

#### Acceptance Criteria

1. WHEN the Omni_Locked_Filters configuration includes tag filters, THE setting SHALL store each tag filter value as the tag's unique Tag_ID rather than the tag's display name.
2. WHEN applying omni locked filters, THE backend SHALL match chits whose tags list contains tags corresponding to the specified Tag_IDs.
3. WHEN displaying omni locked filter configuration in the settings page or the sidebar locked-filter indicator, THE frontend SHALL resolve each stored Tag_ID to the tag's current display name, showing the resolved name to the user.
4. IF a Tag_ID stored in Omni_Locked_Filters no longer corresponds to any existing tag (e.g., the tag was deleted), THEN THE system SHALL silently omit that filter entry from the applied filter set and SHALL NOT display it in the locked filter configuration UI.
5. WHEN a user saves locked filters that include tag selections, THE system SHALL look up the Tag_ID for each selected tag name and persist the Tag_ID values in the Omni_Locked_Filters JSON field.

### Requirement 8: Recent Tags by ID

**User Story:** As a user, I want my recent tags list to track tags by ID, so that renaming a tag does not cause it to disappear from my recents.

#### Acceptance Criteria

1. THE Recent_Tags setting SHALL store recently used tags as an ordered list of Tag_IDs with a maximum of 5 entries.
2. WHEN a user selects a tag in the tag picker or editor, THE frontend SHALL add that tag's Tag_ID to the front of the Recent_Tags list, removing any existing duplicate of the same Tag_ID before insertion.
3. WHEN displaying recent tags in the tag picker, THE frontend SHALL resolve each Tag_ID to its current display name and color from the Tag_Registry.
4. IF a Tag_ID in the recent tags list references a tag that no longer exists in the Tag_Registry, THEN THE frontend SHALL omit that entry from the displayed recents.
5. WHEN the Recent_Tags list exceeds 5 entries after insertion, THE frontend SHALL truncate the list by removing the oldest entries beyond the fifth position.

### Requirement 9: Frontend Tag Display — IDs Hidden from Users

**User Story:** As a user, I want to interact with tags purely by their display names, so that the underlying ID system is invisible to me.

#### Acceptance Criteria

1. THE frontend SHALL display only tag names (never Tag_IDs) in all user-facing contexts: tag picker, tag chips on chits, sidebar filters, settings pages, rule editor, and kiosk view.
2. WHEN the user creates a tag, THE frontend SHALL send the tag name to the backend, and THE backend SHALL generate and assign the Tag_ID.
3. WHEN the user selects a tag (in editor, filters, rules, or any other tag interaction), THE frontend SHALL transmit the corresponding Tag_ID to the backend.
4. THE frontend SHALL maintain a local lookup map (Tag_ID → Tag_Name, Tag_Name → Tag_ID) loaded from the settings tag list endpoint and SHALL refresh this map on page load and after any tag creation, rename, or deletion operation.
5. IF the frontend encounters a Tag_ID that has no corresponding entry in the local lookup map, THEN THE frontend SHALL display the tag using a fallback label indicating an unknown tag and SHALL trigger a map refresh from the backend.

### Requirement 10: Seamless Tag Rename

**User Story:** As a user, I want to rename a tag and have the change reflected everywhere instantly, so that I never have to manually update chits, rules, or filters after a rename.

#### Acceptance Criteria

1. WHEN a tag is renamed, THE Tag_Registry SHALL update the name field on the tag object identified by its Tag_ID, preserving all other fields (color, fontColor, favorite) unchanged.
2. WHEN a tag is renamed, THE Tag_Registry SHALL reject the rename IF the new name matches an existing tag name for that user (case-insensitive comparison), OR IF the new name is empty, OR IF the new name exceeds 200 characters.
3. IF a tag rename is rejected due to validation failure, THEN THE backend SHALL return an error response indicating the reason (duplicate name, empty name, or exceeds length limit) and THE Tag_Registry SHALL remain unchanged.
4. WHEN a tag is successfully renamed on the backend, THE frontend SHALL re-fetch the Tag_Registry from the settings API on the next page load or settings sync, and update all visible tag displays (chips, filter labels, sidebar tree, editor tag list) to show the new name.
5. WHEN a tag is renamed, THE backend SHALL NOT need to update any chit records, rule conditions, filter configurations, or other references because all references use the Tag_ID.
6. IF the user renames a tag while viewing a page that displays that tag, THEN THE frontend SHALL reflect the new name no later than the next settings fetch without requiring a full page reload.

### Requirement 11: Data Migration from Name-Based to ID-Based System

**User Story:** As a system administrator, I want existing tag data to be migrated to the new ID-based system automatically, so that no data is lost during the transition.

#### Acceptance Criteria

1. WHEN the migration runs, THE Migration_Engine SHALL assign a new UUID v4 to each existing tag entry in the Tag_Registry (settings.tags), preserving the existing name, color, fontColor, and favorite properties unchanged.
2. WHEN the migration runs, THE Migration_Engine SHALL convert all chit tags fields from lists of name strings to lists of the corresponding Tag_IDs, matching tag names case-insensitively against the Tag_Registry.
3. WHEN the migration runs, THE Migration_Engine SHALL convert shared_tags entries from tag name references to Tag_ID references, replacing the "tag" field value in each entry with the corresponding Tag_ID.
4. WHEN the migration runs, THE Migration_Engine SHALL convert custom_view_filters tag filter values from name strings to Tag_IDs.
5. WHEN the migration runs, THE Migration_Engine SHALL convert kiosk_selected_tags from name strings to Tag_IDs.
6. WHEN the migration runs, THE Migration_Engine SHALL convert omni_locked_filters tag values from name strings to Tag_IDs.
7. WHEN the migration runs, THE Migration_Engine SHALL convert recent_tags from name strings to Tag_IDs.
8. WHEN the migration runs, THE Migration_Engine SHALL convert rules engine conditions that use tag_present or tag_not_present operators from name values to Tag_ID values.
9. IF a tag name referenced in a chit or configuration does not exist in the Tag_Registry, THEN THE Migration_Engine SHALL create a new tag entry with that name, a generated UUID v4 Tag_ID, no color, no fontColor, and favorite set to false, then use that ID for the reference.
10. THE Migration_Engine SHALL be idempotent — IF a tag entry already contains a valid UUID v4 id field, THEN THE Migration_Engine SHALL skip ID assignment for that entry, and IF a chit tags field already contains UUID v4 values rather than name strings, THEN THE Migration_Engine SHALL skip conversion for that chit.
11. IF the migration encounters a database write failure during conversion, THEN THE Migration_Engine SHALL roll back all changes within the current transaction and report an error message indicating which step failed, leaving the data in its pre-migration state.
12. WHEN the migration runs, THE Migration_Engine SHALL complete all conversions within a single database transaction, ensuring that either all references are converted or none are.

### Requirement 12: System Tags Remain Name-Based

**User Story:** As a backend developer, I want system tags (CWOC_System/ prefix) to remain name-based and excluded from the ID system, so that auto-computed tags continue to work without requiring registry entries.

#### Acceptance Criteria

1. WHEN computing tags for a chit, THE backend SHALL generate system tags as plain name strings (prefixed with "CWOC_System/") and SHALL NOT assign or reference Tag_IDs for any tag whose name starts with "CWOC_System/" (case-insensitive).
2. WHEN merging user tags and system tags on a chit, THE backend SHALL store both in the same `tags` JSON array on the chit record, with system tags represented as name strings and user tags represented as Tag_IDs, preserving both formats in a single list.
3. WHEN rendering a chit's tags, THE frontend SHALL identify system tags by checking whether the tag name starts with "CWOC_System/" (case-insensitive) and SHALL display them by their name string without performing a Tag_Registry lookup.
4. THE Tag_Registry SHALL NOT contain entries for any tag whose name starts with "CWOC_System/" (case-insensitive).
5. IF a Tag_Registry write operation receives a tag name starting with "CWOC_System/" (case-insensitive), THEN THE backend SHALL reject the entry and return an error response indicating that system tags cannot be registered.
6. THE backend SHALL treat tags with the "Habits" or "Habits/" prefix as system-computed tags subject to the same name-based rules as "CWOC_System/" prefixed tags, excluding them from the Tag_Registry and Tag_ID assignment.

### Requirement 13: API Contract — Tag Resolution in Responses

**User Story:** As a frontend developer, I want the API to return resolved tag information alongside IDs, so that the frontend can display tag names without additional lookups for each chit.

#### Acceptance Criteria

1. WHEN the API returns a chit, THE response SHALL include the tags field as a list of objects containing both the Tag_ID and the resolved tag name (e.g., `[{"id": "uuid", "name": "Work/Projects"}]`).
2. WHEN the API returns a chit with system tags, THE response SHALL include system tags as objects with a null ID and the name string (e.g., `[{"id": null, "name": "CWOC_System/Calendar"}]`).
3. WHEN the API returns settings, THE Tag_Registry (settings.tags) SHALL include the full tag objects with id, name, color, fontColor, and favorite fields.
4. THE API SHALL accept tag submissions from the frontend as either Tag_IDs (for existing tags) or new tag names (for inline tag creation).
5. IF the frontend submits a tag name that does not exist in the user's Tag_Registry, THEN THE API SHALL create a new entry in the Tag_Registry with that name, a generated Tag_ID, color set to null, fontColor set to null, and favorite set to false, and return the chit response with the new tag included.
6. IF the frontend submits a tag name beginning with the reserved prefix "CWOC_System/" (case-insensitive), THEN THE API SHALL strip that tag from the submission and not persist it, since system tags are computed automatically from chit properties.

### Requirement 14: Hierarchical Tag Path Preservation

**User Story:** As a user with hierarchical tags, I want the "/" path separator behavior to continue working with the ID system, so that my tag tree structure is preserved.

#### Acceptance Criteria

1. THE Tag_Registry SHALL store hierarchical tags as complete path strings in the name field (e.g., "Work/Projects/CWOC"), with each full path having its own unique Tag_ID, supporting a maximum path depth of 10 levels and a maximum total path length of 512 characters.
2. WHEN filtering by a parent tag, THE frontend SHALL match chits that have the parent tag itself (exact match) OR any tag whose resolved name starts with the parent path followed by "/" (hierarchical matching uses resolved names, not IDs).
3. WHEN a parent tag is renamed, THE Tag_Registry SHALL also rename all child tags that share the old parent path prefix (updating their name fields while preserving their individual Tag_IDs).
4. IF renaming a parent tag would cause any child tag's new path to collide with an existing tag path in the Tag_Registry, THEN THE Tag_Registry SHALL reject the rename and return an error indicating which path(s) conflict.

### Requirement 15: Android App Tag ID Synchronization

**User Story:** As a mobile user, I want the Android app to use the same Tag_ID system, so that tags sync correctly between web and mobile.

#### Acceptance Criteria

1. WHEN the Android app syncs settings, THE app SHALL store the Tag_Registry as a list of tag objects each containing: id (Tag_ID string), name (string), color (string or null), fontColor (string or null), and favorite (boolean).
2. WHEN the Android app syncs chits, THE app SHALL store and transmit user tags as lists of Tag_ID strings, and store system tags (CWOC_System/ prefix) as name strings without Tag_ID resolution.
3. WHEN the Android app displays tags, THE app SHALL resolve each Tag_ID to its display name and color using the local Tag_Registry cache. IF a Tag_ID does not exist in the local Tag_Registry, THEN THE app SHALL omit that tag from the display.
4. WHEN the Android app creates a new tag while online, THE app SHALL send the tag name to the server and receive back the assigned Tag_ID before adding the tag to the local Tag_Registry.
5. IF the Android app creates a new tag while offline, THEN THE app SHALL queue the tag creation request and SHALL NOT assign a local Tag_ID, deferring ID assignment until the server responds on next sync.
6. THE Android app Room database schema SHALL store the chit tags field as a JSON-serialized list of Tag_ID strings (matching the server storage format), and SHALL store the Tag_Registry as a JSON-serialized list of tag objects in the settings entity.
7. WHEN the Android app receives a settings sync that includes an updated Tag_Registry, THE app SHALL replace the local Tag_Registry cache with the server version and re-resolve any currently displayed tag names.
