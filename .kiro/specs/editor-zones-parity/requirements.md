# Requirements Document

## Introduction

This spec covers the remaining Android parity gaps from Web Function Index items W73–W99 for the chit editor zones. It addresses four feature groups: the People zone expand modal, user-defined custom zones in the editor, health indicator conditional display / unit switching / range highlighting, and recurrence series info and actions. These are the final editor-zone gaps needed to reach full web parity on Android.

## Glossary

- **Chit_Editor**: The Android chit editing screen (`ChitEditorScreen.kt`) and its ViewModel (`ChitEditorViewModel`)
- **People_Zone**: The composable section of the Chit_Editor that manages people assignments, shares, and the contact tree
- **Expand_Modal**: A full-screen dialog or ModalBottomSheet that presents the complete People_Zone content in a larger viewport
- **Custom_Zone**: A user-defined zone created via the Custom Objects editor, containing assigned custom objects rendered as input fields in the Chit_Editor
- **Custom_Object**: A user-defined data field with a name, value_type (integer, decimal, boolean, string), optional units, metric_units, range_min, range_max, and conditional_display rule
- **Health_Indicators_Zone**: The composable section of the Chit_Editor that renders health indicator input fields from the indicators_zone
- **Conditional_Display_Rule**: A JSON object `{setting: "<key>", equals: "<value>"}` that determines whether a Custom_Object is visible based on user settings
- **Range_Highlight**: A visual indicator (colored background) applied to a numeric input field when its value falls outside the object's range_min/range_max bounds
- **Unit_System**: The user's preference for imperial or metric units, stored in settings as `unit_system`
- **Health_Data**: A JSON field on the chit (`health_data`) that stores UUID-keyed values for both health indicators and custom zone fields
- **Recurrence_Series**: The full set of virtual instances generated by a recurring chit's recurrence_rule
- **Series_Info**: Computed metadata for a recurrence series: instance number, total past instances, completed count, and success rate
- **Series_Summary**: A visual UI component showing all instances of a recurring chit with their completion status (completed, missed, broken off, upcoming)
- **Break_Off**: The action of converting a single virtual recurring instance into a standalone chit and adding an exception to the parent
- **Auto_Archive**: The automatic archiving of a recurring chit when all instances up to its end date are completed or broken off
- **ChitEditorViewModel**: The ViewModel managing editor state, API calls, and save logic for the Chit_Editor
- **QuickEditSheet**: The bottom sheet modal used for quick-editing chits from list/calendar views
- **RecurrenceEngine**: The Android utility class that expands recurrence rules into virtual instances

## Requirements

### Requirement 1: People Zone Expand Modal

**User Story:** As a user, I want to expand the People zone into a full-screen modal, so that I have more space to manage people, shares, and the contact tree on mobile.

#### Acceptance Criteria

1. WHEN the user taps the expand button in the People_Zone header, THE Chit_Editor SHALL display the Expand_Modal containing the people list (contacts and system users), sharing controls, search input, and stealth toggle
2. THE Expand_Modal SHALL render as a full-screen Dialog or ModalBottomSheet that occupies the full viewport, scrollable if content exceeds the visible area
3. WHEN the user dismisses the Expand_Modal via the close button, back gesture, or swipe down, THE Chit_Editor SHALL close the modal and return focus to the People_Zone section
4. WHILE the Expand_Modal is open, THE Chit_Editor SHALL allow the user to add and remove people, add and remove shared users, change share roles, set the assigned-to user, toggle stealth, and search/filter the contact tree — all operating on the same in-memory state as the inline People_Zone so that changes are immediately reflected without a separate sync step

### Requirement 2: Fetch Custom Zones from API

**User Story:** As a user, I want the chit editor to load my custom zones, so that I can enter data for my user-defined fields when editing a chit.

#### Acceptance Criteria

1. WHEN the Chit_Editor loads a chit, THE ChitEditorViewModel SHALL fetch the user's custom zones from the `/api/custom-zones` endpoint and, for each zone returned, fetch the assigned Custom_Objects from `/api/custom-objects/zone/{zone_id}` in sort_order sequence
2. WHEN custom zones and their assigned objects are fetched, THE Chit_Editor SHALL render each zone that has at least one visible object as a collapsible Zone_Panel, ordered by the zone's sort_order
3. IF the `/api/custom-zones` endpoint returns an error or a non-200 status, THEN THE Chit_Editor SHALL continue loading without custom zone panels and log the error
4. IF a zone's `/api/custom-objects/zone/{zone_id}` endpoint returns an error or a non-200 status, THEN THE Chit_Editor SHALL skip rendering that zone's panel and continue fetching and rendering the remaining zones
5. IF the `/api/custom-zones` endpoint returns an empty array, THEN THE Chit_Editor SHALL complete loading without rendering any custom zone panels and without displaying an error

### Requirement 3: Render Custom Zone Panels

**User Story:** As a user, I want my custom zones to appear as collapsible sections in the chit editor, so that I can view and edit my custom data fields.

#### Acceptance Criteria

1. THE Chit_Editor SHALL render each Custom_Zone as a collapsible section with the zone name as the header, initially expanded if any field within the zone has a stored value in the chit's health_data, and initially collapsed otherwise
2. THE Chit_Editor SHALL render input fields for each Custom_Object assigned to the zone, using the appropriate input type based on value_type: numeric input (step=1) for integer, numeric input (step=any) for decimal, checkbox for boolean, and text input for string
3. THE Chit_Editor SHALL group Custom_Objects within a zone by sub_type (falling back to type, then "Other" if both are null), with each group rendered as a collapsible sub-section sorted alphabetically by group name
4. THE Chit_Editor SHALL sort Custom_Objects within each group by zone_sort_order ascending, treating null zone_sort_order as 0
5. WHEN a Custom_Zone has no visible objects (all filtered out by Conditional_Display_Rules), THE Chit_Editor SHALL hide that zone panel entirely

### Requirement 4: Custom Zone Data Persistence

**User Story:** As a user, I want my custom zone field values to be saved with the chit, so that my data persists across editing sessions.

#### Acceptance Criteria

1. WHEN the Chit_Editor loads a chit with existing Health_Data, THE Chit_Editor SHALL parse the Health_Data JSON and populate each custom zone field whose Custom_Object UUID appears as a key in that JSON with the corresponding stored value
2. WHEN the user modifies a custom zone field value, THE Chit_Editor SHALL mark the chit as unsaved
3. WHEN the user saves the chit, THE Chit_Editor SHALL merge custom zone field values (excluding null and empty-string values) with indicator zone values into a single UUID-keyed Health_Data JSON object and persist it via the save API call without overwriting indicator zone entries
4. THE Chit_Editor SHALL store custom zone values using the Custom_Object UUID as the key in Health_Data, matching the web implementation's storage format
5. IF the save API call fails, THEN THE Chit_Editor SHALL retain the unsaved state and display an error message indicating the save failed

### Requirement 5: Conditional Display for Health Indicators

**User Story:** As a user, I want health indicators with conditional display rules to be hidden when my settings don't match, so that I only see relevant indicators (e.g., pregnancy indicators hidden for male users).

#### Acceptance Criteria

1. WHEN the Health_Indicators_Zone loads indicator objects, THE Health_Indicators_Zone SHALL evaluate each object's Conditional_Display_Rule by comparing the current user's setting value at the rule's `setting` key against the rule's `equals` value using strict equality
2. WHEN a Conditional_Display_Rule is present and the user's setting value does not equal the rule's `equals` value, THE Health_Indicators_Zone SHALL hide that indicator field completely (no placeholder or empty space)
3. WHEN a Custom_Object has no Conditional_Display_Rule (null or absent), THE Health_Indicators_Zone SHALL display that indicator unconditionally
4. IF a Conditional_Display_Rule references a setting key that does not exist in the user's settings, THEN THE Health_Indicators_Zone SHALL treat the rule as non-matching and hide that indicator field
5. WHEN the Chit_Editor loads Custom_Objects for Custom_Zones, THE Chit_Editor SHALL apply the same Conditional_Display_Rule evaluation to each Custom_Object before rendering its input field

### Requirement 6: Unit Label with Metric Support

**User Story:** As a user, I want health indicator unit labels to reflect my unit system preference, so that I see metric units when I have metric selected in settings.

#### Acceptance Criteria

1. WHEN the user's Unit_System setting is "metric" and a Custom_Object has a `metric_units` field that is not null and not an empty string, THE Health_Indicators_Zone SHALL display the `metric_units` value as the unit label for that field
2. WHEN the user's Unit_System setting is "imperial", THE Health_Indicators_Zone SHALL display the Custom_Object's `units` field value as the unit label regardless of whether `metric_units` is populated
3. IF the user's Unit_System setting is "metric" and a Custom_Object has a null or empty-string `metric_units` field, THEN THE Health_Indicators_Zone SHALL fall back to displaying the `units` field value as the unit label
4. THE Health_Indicators_Zone SHALL display unit labels only for Custom_Objects with value_type "integer" or "decimal"; Custom_Objects with value_type "boolean" or "string" SHALL NOT display a unit label
5. THE Health_Indicators_Zone SHALL store raw numeric values without unit conversion — the unit label is display-only and does not transform the stored value
6. THE Chit_Editor SHALL apply the same unit label selection logic (criteria 1 through 3) to Custom_Objects rendered in Custom_Zones

### Requirement 7: Range Highlight for Out-of-Range Values

**User Story:** As a user, I want numeric indicator fields to be visually highlighted when my entered value is outside the acceptable range, so that I can quickly identify abnormal readings.

#### Acceptance Criteria

1. WHEN a numeric indicator field value exceeds the Custom_Object's `range_max`, THE Health_Indicators_Zone SHALL apply a high-range visual highlight (orange/red background tint) to that field
2. WHEN a numeric indicator field value is below the Custom_Object's `range_min`, THE Health_Indicators_Zone SHALL apply a low-range visual highlight (blue background tint) to that field
3. WHEN a numeric indicator field value is within the range_min and range_max bounds (inclusive), THE Health_Indicators_Zone SHALL display the field with no range highlight (default background)
4. WHEN the user changes a numeric field value, THE Health_Indicators_Zone SHALL update the range highlight in real time without requiring a save or refresh
5. WHEN a Custom_Object has no range_min and no range_max defined (both null), THE Health_Indicators_Zone SHALL never apply range highlighting to that field
6. WHEN only range_min is defined (range_max is null), THE Health_Indicators_Zone SHALL only check the low-range condition; WHEN only range_max is defined (range_min is null), THE Health_Indicators_Zone SHALL only check the high-range condition
7. WHEN the field value is empty or non-numeric, THE Health_Indicators_Zone SHALL not apply any range highlight
8. THE Chit_Editor SHALL apply the same range highlight logic to numeric Custom_Objects in Custom_Zones

### Requirement 8: Recurrence Series Info Computation

**User Story:** As a user, I want to see statistics about my recurring chit series, so that I can track my completion rate and progress.

#### Acceptance Criteria

1. WHEN a recurring chit is displayed in the QuickEditSheet, THE RecurrenceEngine SHALL compute the Series_Info containing: the instance number of the current virtual date within the series, total past instances up to and including today, completed count, and success rate percentage
2. THE RecurrenceEngine SHALL walk the recurrence rule from the chit's calendar start date, advancing by the rule's frequency and interval, counting instances up to today, excluding dates that have a recurrence_exception entry with broken_off equal to true
3. THE RecurrenceEngine SHALL count instances whose date matches a recurrence_exception entry with completed equal to true as completedPast
4. THE RecurrenceEngine SHALL calculate success rate as `round((completedPast / totalPast) * 100)`, returning 0 when totalPast is 0
5. IF the chit has no recurrence_rule or the recurrence_rule has no freq value, THEN THE RecurrenceEngine SHALL return null for Series_Info
6. THE RecurrenceEngine SHALL limit iteration to a maximum of 730 generated dates to prevent unbounded computation for long-running or high-frequency recurrences

### Requirement 9: Series Summary UI

**User Story:** As a user, I want to see a visual summary of all instances in my recurring series, so that I can see which ones I completed, missed, or broke off.

#### Acceptance Criteria

1. WHEN a recurring chit is opened in the QuickEditSheet or Chit_Editor, THE Chit_Editor SHALL render a Series_Summary showing instances listed in chronological order (oldest first) with their completion status
2. THE Series_Summary SHALL display each instance with a status icon: ✅ for completed (date present in recurrence_exceptions with completed=true), ❌ for missed (instance date is before today and not completed or broken off), ✂️ for broken off (date present in recurrence_exceptions with broken_off=true), ⬜ for upcoming (instance date is today or in the future)
3. THE Series_Summary SHALL show instances from the series start date up to 30 days in the future, with a maximum of 50 instances displayed, within a scrollable container
4. THE Series_Summary SHALL display the date and abbreviated day-of-week for each instance alongside its status icon
5. IF the recurring chit has no start date or the recurrence_rule is missing, THEN THE Series_Summary SHALL not render

### Requirement 10: Complete Series Action

**User Story:** As a user, I want to mark an entire recurring series as Complete, so that I can close out a recurring chit when I'm done with it.

#### Acceptance Criteria

1. WHEN the user selects the "Complete Series" action on a recurring chit, THE Chit_Editor SHALL prompt the user for confirmation before proceeding
2. WHEN the user confirms the "Complete Series" action, THE Chit_Editor SHALL set the parent chit's status to "Complete" and record the completed_datetime as the current UTC timestamp in ISO 8601 format
3. WHEN the "Complete Series" action succeeds, THE Chit_Editor SHALL persist the status change via the API
4. IF the API call to fetch or save the parent chit fails, THEN THE Chit_Editor SHALL display an error toast indicating the series could not be completed and leave the chit status unchanged

### Requirement 11: Break Off Instance Action

**User Story:** As a user, I want to break off a single recurring instance into a standalone chit, so that I can edit it independently without affecting the rest of the series.

#### Acceptance Criteria

1. WHEN the user selects the "Break Off" action on a virtual recurring instance, THE Chit_Editor SHALL create a new standalone chit as a copy of the parent chit with the virtual instance's specific start_datetime, end_datetime, and due_datetime values, and a newly generated unique ID
2. WHEN creating the new standalone chit, THE Chit_Editor SHALL set recurrence_rule, recurrence_exceptions, recurrence, and recurrence_id to null on the new chit
3. WHEN the new standalone chit is successfully created, THE Chit_Editor SHALL add an exception entry with the instance date and broken_off set to true to the parent chit's recurrence_exceptions list
4. WHEN the break-off operation completes successfully, THE Chit_Editor SHALL navigate to the new standalone chit in the editor
5. IF the parent chit cannot be fetched or the new chit cannot be created or the exception cannot be added to the parent, THEN THE Chit_Editor SHALL display an error toast indicating the failure reason, shall not navigate away from the current view, and shall not leave a partial broken-off state (no orphaned standalone chit without a corresponding parent exception)

### Requirement 12: Auto-Archive Recurring Chit

**User Story:** As a user, I want my recurring chits to be automatically archived when all instances are done, so that completed series don't clutter my active views.

#### Acceptance Criteria

1. WHEN a recurrence exception is added or modified (completion or break-off) on a recurring chit that has an end date (rule.until), THE Chit_Editor SHALL evaluate whether all instances from start_datetime through the end date are each covered by a recurrence exception marked as completed or broken_off
2. IF the chit has no end date (rule.until is null or absent), THEN THE Chit_Editor SHALL skip the auto-archive evaluation
3. IF the chit's end date (rule.until) is later than the current date at the time of evaluation, THEN THE Chit_Editor SHALL skip the auto-archive evaluation
4. IF the chit is already archived (archived flag is true), THEN THE Chit_Editor SHALL skip the auto-archive evaluation
5. IF all generated instances (determined by start_datetime, freq, interval, and byDay up to rule.until) each have a corresponding recurrence exception with completed=true or broken_off=true, THEN THE Chit_Editor SHALL set the chit's archived flag to true and status to "Complete"
